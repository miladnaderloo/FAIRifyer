# FAIRifyer

[![License](https://img.shields.io/badge/license-Apache--2.0-blue.svg)](LICENSE)
[![fair-software.eu](https://img.shields.io/badge/fair--software.eu-%E2%97%8F%20%20%E2%97%8F%20%20%E2%97%8F%20%20%E2%97%8F%20%20%E2%97%8B-yellow)](https://fair-software.eu)

Turn a folder of raw X-ray CT scan output into FAIR metadata, without asking the
scientist to fill in a form.

Point FAIRifyer at a dataset directory. It finds the vendor log files, harvests
the key/value pairs, maps the vendor's vocabulary onto a canonical schema,
converts the units, validates the result against a JSON Schema, and writes a
machine-readable metadata record plus a human-readable README ready for deposit
in 4TU.ResearchData or Zenodo.

Developed for the [EXCITE²](https://excite-network.eu) imaging infrastructure
and funded by the 4TU FAIR Data Fund.

## Why

Imaging facilities produce metadata that is complete but unusable: every vendor
names the same physical quantity differently, units are inconsistent, and the
information is buried in proprietary log files. Researchers are then asked to
re-enter it by hand at deposit time, so they do not. FAIRifyer removes the
manual step, which is the step where FAIR metadata is actually lost.

## Install

```bash
git clone https://github.com/miladnaderloo/FAIRifyer.git
cd FAIRifyer
pip install -e .
```

The AI matching stage is optional. Without it, FAIRifyer falls back to string
similarity and still runs:

```bash
pip install -e ".[ai]"
```

Requires Python 3.8 or newer.

## Use

Command line:

```bash
fairify path/to/dataset --out metadata_excite.json
```

Python:

```python
from fairify import fairify, fairify_with_readme, fairify_excite2

# flat record, with validation report and per-field similarity scores
record = fairify("path/to/dataset")

# same, plus a deposit-ready README.txt
record = fairify_with_readme("path/to/dataset")

# record structured around the EXCITE2 graph data model
record = fairify_excite2("path/to/dataset")
```

## How it works

```
find files → parse → translate terms → normalise units → build record → validate
```

Term translation is deliberately two-stage:

1. **Regex against a curated synonym table.** Fast, deterministic, and covers the
   vendor vocabularies already seen. Every known key resolves here.
2. **Sentence-transformer embeddings** (`all-MiniLM-L6-v2`) for keys the table
   does not recognise, accepted only above a cosine similarity of 0.82. If
   `sentence-transformers` is not installed the stage degrades to `difflib`
   rather than failing.

The deterministic stage runs first on purpose. The model is there to handle the
long tail of unseen vendor keys, not to second-guess mappings that are already
known to be correct. Every field carries its similarity score in the output, so
a curator can see which values were matched by rule and which by model.

Two output shapes are available side by side. `fairify()` produces a flat
record with acquisition, reconstruction and extended blocks. `fairify_excite2()`
produces the EXCITE² graph model (nodes: sample, site, operator, instrument,
software, license; edges: sampling, sample_processing, measuring) defined in
deliverable D4.2. The graph pipeline is extraction only: every field is either
filled from a real vendor key found in the dataset or left null.

## Output

- `metadata_excite.json` — machine-readable record, JSON-LD with a schema.org
  context, validated against `schemas/excite_ct_schema_v1.json`
- `README.txt` — human-readable dataset documentation following the EPFL Library
  README best practices, with placeholders for DOI, licence and access
  conditions to be completed at deposit

## Schemas

| File | Purpose |
| --- | --- |
| `schemas/excite_ct_schema_v1.json` | flat CT acquisition and reconstruction record |
| `schemas/excite2_graph_schema_v1.json` | EXCITE² graph data model |

Both are versioned. Breaking changes get a new `_v2` file rather than an edit in
place, so records generated by earlier releases stay validatable.

## Status

Version 0.1.0. The interface may still change before 1.0.0. A test suite covering
the parsers, normaliser, validators and an end-to-end integration run is
maintained alongside development and will be published once its sample data has
been replaced with synthetic vendor logs.

## Contributing

Bug reports, vendor formats we do not yet handle, and schema feedback are all
welcome. See [CONTRIBUTING.md](CONTRIBUTING.md). If FAIRifyer fails on output
from an instrument we have not seen, an issue with a redacted log file is the
most useful thing you can send.

## Citation
